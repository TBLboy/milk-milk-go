# TASK-114 错误二维码不上传类型确认照片

## 1. 背景

APP 类型确认当前在实时识别到二维码后立即抓拍并上传照片，然后才由后端校验标签是否存在、是否有效、标签辅料与扫描结果是否一致，以及扫描辅料是否匹配当前工单步骤。因此，即使扫描的是错误二维码，也会在后端留下无业务价值的照片证据。

## 2. 业务规则

- 类型确认扫描到二维码后，先校验标签类型和辅料匹配关系，不得先抓拍或上传照片。
- 校验内容包括：
  - 当前用户是管理员或当前工单执行人；
  - 当前步骤允许类型确认；
  - 标签存在且状态为 `active`；
  - 标签的 `materialId` 与二维码扫描结果一致；
  - 扫描结果的 `materialId` 与当前工单步骤快照一致。
- 任一校验失败时：
  - 不上传照片；
  - 不创建证据文件；
  - 不推进步骤状态；
  - APP 显示后端返回的具体原因并继续允许扫描。
- 校验通过后才从当前现场画面抓拍、添加水印、上传照片并提交正式类型确认。
- 正式确认接口必须再次执行相同校验，防止客户端绕过或校验后标签失效等竞态。
- 无码拍照申请流程不受本次修改影响，仍按现场拍摄包装照片并提交管理员审批执行。

## 3. 实施范围

- 后端新增二维码轻量预校验接口，不接收证据文件。
- 提取二维码校验逻辑，供预校验和正式确认复用。
- APP Repository 增加预校验调用。
- APP 自动扫码流程改为“预校验通过 -> 抓拍 -> 上传 -> 正式确认”。
- 增加后端预校验成功、失败和不产生证据文件的测试。

## 4. 验收条件

- 正确正式标签预校验返回成功，随后可以正常完成类型确认。
- 未知标签、失效标签、标签辅料不一致、工单步骤辅料不一致时预校验返回 `422`。
- 预校验失败不新增 `EvidenceFile`，不产生上传文件。
- APP 源码中抓拍和上传只能发生在预校验成功之后。
- 正式确认接口继续保留原有防错和状态推进逻辑。
- 后端专项与完整回归、Android Kotlin 编译和 Lint、差异检查通过。
- Android `1.0.11` APK 构建、v2/v3 签名和 SHA-256 校验通过。

## 6. 限制

- 真实 Android 平板需回归错误二维码连续对准、正确二维码自动确认和无码拍照申请。
- 若标签在预校验成功后、正式确认前被管理员作废，仍可能已产生照片；正式确认会拒绝推进步骤，但两端并发处理不在本次范围内。
