# TASK-111 修复注册历史账号串入与工单执行人越权

## 1. 背景

进入注册模式后，登录页保存的账号仍可能因输入框复用、焦点保留或 Android 自动填充浮层出现在注册账号栏。与此同时，普通操作员只要能看到工单，就可以在 App 中执行类型确认、开始工单、提交完成和申请撤销，没有校验当前账号是否真的是工单执行人。

## 2. 业务规则

- 登录账号与注册账号使用独立输入状态。
- 进入或退出注册模式时，必须重新建立账号输入框并清除当前焦点，避免登录保存账号和系统自动填充浮层串入。
- 注册模式继续排除 Android 自动填充；登录模式保留应用自己的记住密码能力。
- 普通操作员只有 `order.operator_id == current_user.id` 才能执行工单步骤、开始工单、提交完成和申请撤销。
- 工单创建人身份不等于执行权限；工单被接管或指派给其他人后，原创建人只能查看并申请接管。
- 管理员保留后台管理权限；管理员同时也是执行人时，可以在 App 中操作该工单。
- 其他普通操作员仍可查看工单状态，但只能申请接管。

## 3. 实施范围

- 注册账号输入框在模式切换时使用独立 Compose identity，并主动清除焦点。
- 注册账号、注册密码和确认密码使用独立状态。
- App 工单详情按执行人身份控制按钮显示。
- 后端开始、完成、证据提交和撤销申请统一校验当前执行人。
- 增加非执行人操作和接管后原创建人失去执行权限的回归测试。

## 4. 验收条件

- 登录页有已记住账号时，进入注册页后注册账号栏为空，不显示登录账号下拉数据。
- 从注册页返回登录页后，登录页原有账号回填与记住密码不丢失。
- 非执行人的普通操作员看不到类型确认、填写称重、开始执行、提交完成和申请撤销按钮。
- 即使绕过界面直接调用接口，非执行人操作返回 `403 WORK_ORDER_OPERATOR_REQUIRED`。
- 工单被接管后，原创建人不能开始或执行该工单。
- 管理员或当前执行人可以执行符合状态条件的操作。
- 后端专项与完整回归、Android 编译和 Lint、差异检查、APK v2/v3 签名与哈希校验通过。
