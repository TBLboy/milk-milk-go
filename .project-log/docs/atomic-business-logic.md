# 原子业务逻辑编写指南

## 原子判断测试

一条规则满足以下条件时，颗粒度通常合适：

1. 能用一句核心 rule 表达；
2. 可以独立判断通过或失败；
3. 可以单独变更而不必重写多个无关行为；
4. 可以映射到实现和测试证据；
5. 业务人员能理解其可观察结果。

## 应拆分的信号

- 规则中包含“并且”，两部分可以分别失败；
- 同时处理成功、失败、权限和通知等多个结果；
- 验收条件需要完全不同的环境；
- 不同角色对规则拥有不同决定权；
- 一部分改变时另一部分无需改变。

## 不应拆得过细的信号

- 只是函数内部算法步骤；
- 只是变量赋值或文件编辑；
- 没有独立业务意义；
- 无法形成独立可观察验收结果。

## 六种类型

- `flow`：业务流程中的独立步骤；
- `rule`：条件判断与结果；
- `state-transition`：事件引起状态变化；
- `constraint`：始终成立的边界或禁止项；
- `data-contract`：输入、输出和数据语义；
- `integration`：与外部系统/设备的交互规则。

## Authority 与 Status

- `authority` 表示规则来源强度；
- `status` 表示规则当前生命周期。

Agent 推断的规则应为 `draft + inferred`。实验规则为 `experimental`。发现权威冲突时使用 `conflict`，不得选择性忽略证据。

## 功能规则与技术事实

- 功能业务逻辑描述系统应该怎样表现。
- 技术业务逻辑描述当前系统如何承载行为及其强制约束。
- 当前代码、配置或测试行为不能仅凭存在就升级为功能规则。
- 未来实现方案不属于技术业务逻辑，应进入 solution research 和 architecture decision。
