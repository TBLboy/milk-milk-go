# GPT 功能审查意见核查记录

> 核查日期：2026-09-13  
> 核查对象：GPT 对《PC 与平板整体功能审查及软件图标设计任务说明》返回的 P0/P1/P2 意见  
> 代码快照：`7a69e399ebc7a30431f024081b6798c4cd955c99`（工作区包含尚未提交的 APP 侧边栏和用户协议修改）  
> 目的：判断 GPT 意见中哪些是已确认事实、哪些已经实现、哪些与现有业务规则冲突，以及哪些需要客户继续确认。  
> 本轮不修改功能代码，也不把尚待讨论的建议直接写成正式需求。

---

## 1. 总体结论

GPT 对系统成熟度的判断基本准确：

1. 当前系统已有较完整的工单、配方快照、顺序执行、类型确认、称重、审批和追溯骨架。
2. “拿错辅料”已有明确流程约束。
3. “称错重量”目前只能校验人工录入值和目标重量的偏差，并要求保存秤面照片，不能证明照片读数和录入数字严格一致。
4. 当前主要风险集中在生产级闭环、故障恢复、安全、标签实物链路和发布验证，而不是页面数量。
5. 不建议为了“看起来专业”立即把 SQLite 替换为 PostgreSQL；应先基于真实规模验证 SQLite，并补齐可靠性配置。

但 GPT 意见中有几处需要修正或降级：

1. “辅料需要启用/停用”与客户已经明确确认的规则冲突。客户要求辅料只保留新增、编辑和删除，不设置启用/停用；除非客户重新提出，否则不应实施。
2. “超差尝试保存”当前已经实现，不应记录成缺失功能。
3. “人工称重的剩余风险”不是代码错误，而是首版明确接受的能力边界，必须写入验收文件和风险确认。
4. “审计日志需要页面”说得不够准确。当前更严重的问题是审计日志覆盖范围本身很小，不能只补查询页面。
5. GPT 没有直接指出一个关键缺口：平板解析二维码后，只把 `material_id` 提交给后端，没有提交或校验二维码里的 `labelId`。后台因此不能确认该二维码是否由本系统生成、标签是否有效，也不能识别标签作废状态。

## 2. 核查分类

| 分类 | 含义 |
|---|---|
| `confirmed` | 已通过当前代码、配置或项目记录确认 |
| `partial` | 方向正确，但现状比 GPT 描述得更完整或更具体 |
| `conflict` | 与客户已确认业务规则冲突，不能直接采纳 |
| `decision-needed` | 需要客户、工艺、质量、网络或法务确认 |

## 3. P0 意见核查

### P0-1 标签“生成、打印、粘贴、复核”没有真正闭环

**核查结论：`confirmed`，且应列为当前最高优先级。**

当前事实：

1. PC 按钮文字是“生成并打印标签”，但前端只调用 `POST /labels/print-batches`。
2. 后端只创建 `print_batches` 记录和独立 `labels` 记录，批次初始状态固定为 `pending`。
3. 没有调用 Windows 打印队列、打印机 SDK、RAW 指令或 TCP 打印端口。
4. 没有生成可交付打印文件，也没有区分打印成功、失败、结果未知。
5. `pending` 状态没有后续真实打印机回执，也没有人工确认状态。
6. 没有重打原因、作废和贴标后的复核扫码流程。
7. 平板扫码确认时只向后端提交 `material_id` 和证据图片，没有提交 `labelId`。
8. 后端二维码确认接口只比较 `material_id` 与工单步骤要求，不查询 `labels` 表，也不检查标签状态。

证据位置：

- `pc/src/pages/ManagementPages.tsx:539`
- `pc/server/app/api/labels.py:28`
- `pc/server/app/db/models.py:199`
- `app/app/src/main/java/com/muheng/milkweigh/RealMilkRepository.kt:205`
- `pc/server/app/api/evidence.py:76`

应当补强的完整链路：

```text
选择辅料
→ 生成唯一 labelId
→ 创建待打印任务
→ 向真实打印机发送任务
→ 获得成功/失败/结果未知
→ 实物标签粘贴
→ 可选或强制贴标复核
→ 平板扫码并同时提交 materialId + labelId
→ 后端校验标签存在、有效、未作废
→ 校验 materialId 与当前步骤一致
→ 保存打印与复核记录
```

重点：

- 如果客户要求彻底降低“正确二维码贴到错误包装”的风险，贴标后的复核扫码应升级为强制步骤。
- 即使第一版不强制复核，后端也必须校验 `labelId`，否则自制二维码只提供了约定格式，不能形成系统级标签有效性校验。
- 正式打印机型号、标签尺寸、驱动方式和状态回传能力仍是现场输入阻塞项。

### P0-2 无码辅料审批必须定规则

**核查结论：`confirmed`，其中审批岗位和授权方式为 `decision-needed`。**

当前已经实现：

1. 未识别二维码时可以拍照并填写原因。
2. 无码申请必须包含照片和原因。
3. 审批通过前不能称重。
4. 只有管理员角色能批准照片放行。
5. 当前申请天然绑定到具体工单和步骤，不能直接给其他工单复用。

当前尚未固定：

1. 正式生产中谁是唯一或指定审批人。
2. 是否允许远程审批、值班审批或委托审批。
3. 是否禁止申请人自批。当前后端只检查 `role=admin`，管理员同时参与操作时存在自批可能。
4. 审批有效期。当前没有独立的超时失效规则。
5. 无码放行次数统计和异常预警。

因此不能把 GPT 的“审批人不得等于执行人”直接写成既有需求，但应在正式投产规则中明确。

### P0-3 “防称错重量”的能力边界

**核查结论：`partial`。GPT 对边界判断正确，但部分建议已经实现。**

当前已经实现：

1. 页面显示目标重量和允差。
2. 手动输入重量必须同时上传现场拍摄的秤面照片。
3. 后端按 `max(目标重量 × 1%, 5g)` 的默认规则计算允差。
4. 每次提交都会新增 `WeighingAttempt`，超差尝试不会被成功记录覆盖。
5. 只有落在允差内的尝试才会把步骤推进为完成。

当前确实无法保证：

```text
电子秤实际显示值 == 操作员输入值
```

因此正确处理方式是：

1. 将“人工读秤 + 照片追溯”明确写入第一版验收边界。
2. 由客户书面确认首版剩余风险。
3. 如果客户要求系统自动保证秤面值与入库值一致，电子秤直连必须从 P2 提升为 P0。
4. 可增加重量照片人工复核、随机抽检和异常统计，但不能把人工录入描述成自动取重。

证据位置：

- `app/app/src/main/java/com/muheng/milkweigh/MainActivity.kt:2238`
- `pc/server/app/api/evidence.py:125`
- `pc/server/app/db/models.py:186`

### P0-4 备份必须有恢复能力

**核查结论：`confirmed`。**

当前事实：

1. 设置页已有“自动备份”开关和备份时间配置。
2. 但代码中没有定时任务、后台调度器或启动时补偿任务，配置不会真正触发备份。
3. “立即备份数据库”只复制 SQLite 文件。
4. 证据照片、头像、配置、标签相关文件和恢复说明没有进入同一备份单元。
5. 没有恢复界面、恢复校验或恢复演练。
6. 设置页显示“自动备份已启用”会制造功能已经完成的错误印象。

建议的最小生产备份单元：

```text
SQLite 一致性备份
+ uploads/证据文件
+ 必要配置
+ 版本和校验信息
+ 同一备份时间窗口的 manifest
```

验收不能只检查“生成备份文件”，还必须在一台干净环境完成：

```text
安装
→ 导入备份
→ 启动
→ 登录
→ 打开历史工单
→ 查看全部照片、审批、重量和标签记录
→ 数据一致
```

### P0-5 内网 HTTP

**核查结论：`confirmed`，正式投产前属于 `decision-needed` 的 P0 条件项。**

当前事实：

1. Android 默认地址使用 `http://...:8011/api/v1/`。
2. Windows 安装程序也以 HTTP 打开管理端。
3. 服务没有 HTTPS、内部 CA 或证书配置。
4. App 和后端之间会传输登录令牌、头像、电话、身份证信息、审批和现场照片。

“内网”不能自动等同于可信网络。正式投产有两种可接受路径：

1. 使用 HTTPS 和受平板信任的内部证书。
2. 客户明确接受受控独立生产网中的 HTTP 风险，并形成书面风险记录。

该选择会影响安装、证书信任、平板配置和升级维护，实施前需要技术调研与现场网络确认。

### P0-6 SQLite 并发和故障验证

**核查结论：`confirmed`。**

当前事实：

1. 使用 SQLite，允许 `check_same_thread=False`。
2. 已启用外键。
3. 未设置 WAL。
4. 未设置 `busy_timeout`。
5. 没有统一幂等记录。
6. 没有乐观锁或版本号。
7. 目前主要靠业务状态检查，例如已处理审批再次请求返回 `409`，但没有覆盖双击并发和两个设备同时推进步骤的竞态测试。
8. 没有断电、磁盘满、数据库锁和长时间运行测试。

建议先按客户预计最大平板数量做真实并发与故障验证，再决定是否需要调整数据库。不能因为切换到 PostgreSQL 就自动解决业务幂等和状态冲突。

### P0-7 证据服务器侧完整性保护

**核查结论：`confirmed`。**

当前事实：

1. 图片上传后保存文件路径、原文件名、MIME、大小、上传人和时间。
2. 没有 SHA-256 或其它哈希。
3. 文件接口按文件 ID 读取，没有校验磁盘文件是否被替换。
4. 客户端水印可以提高操作门槛，但不能作为防篡改凭证。

建议优先补：

1. 上传后计算并保存 SHA-256。
2. 文件内容不可覆盖；更正只能新增文件记录。
3. 提供后台证据完整性检查。
4. 对数据库路径、文件大小、MIME 和哈希做一致性检查。

这不要求区块链，也不应阻塞其它主流程。

### P0-8 正式安装包和升级验证

**核查结论：`confirmed`。**

当前事实：

1. 已有 Windows 安装器和 Android APK 的构建产物及签名校验。
2. Windows 11 真机全新安装和覆盖升级尚未完成。
3. 安装后数据保留、防火墙、服务自启动、SMTP 和自动备份未做完整实机验证。
4. 后续 APP、用户协议、侧边栏等修改尚未再次冻结成正式 release candidate。

正式投产前必须重新冻结版本并完成：

```text
全新安装
→ 初始化
→ 登录
→ 创建业务数据
→ 覆盖升级
→ 数据保留
→ App 连接
→ 完整工单
→ 卸载行为确认
```

## 4. P1 意见核查

### P1-1 辅料启用/停用

**核查结论：`conflict`，不采纳当前建议。**

客户已经明确确认：

1. 辅料不设置启用/停用状态。
2. 辅料管理只提供新增、编辑和删除。
3. 以前的辅料停用逻辑属于未经确认的错误扩展，已经移除。

因此 GPT 的 P1-1 不能直接进入任务清单。除非客户重新提出主数据生命周期需求，否则保持现状。

可以讨论的是删除保护是否足够：

- 已被配方引用的辅料目前禁止删除。
- 历史工单使用快照保存，不再依赖辅料主表。
- 已使用过的辅料最终仍可能在配方移除后被物理删除。
- 若未来需要更强的历史追溯，应通过删除审计或历史归档解决，但不应擅自恢复“停用”概念。

### P1-2 配方“可用于生产”状态

**核查结论：`partial`，核心规则已经实现。**

当前事实：

1. 产品与配方有启用/停用状态。
2. 停用产品或配方不能创建新工单。
3. 工单创建时保存产品名称、辅料身份、代号、名称、要求重量和允差快照。
4. 已有工单不会因后续配方编辑而改变。
5. 当前数据模型是一个产品对应一个配方。

暂不需要复杂配方版本管理系统，但需要客户确认：

1. 一个产品是否只允许一个可用配方。
2. 配方编辑是否必须新增版本记录。
3. 停用产品是否保留历史工单正常查看。

### P1-3 接管、撤销和审批统一状态机

**核查结论：`partial`。**

当前已经实现：

1. 请求有 `pending / approved / rejected` 状态。
2. 同一工单存在待审批请求时，不能重复创建第二个申请。
3. 已处理申请再次操作会返回状态冲突。

仍需补强：

1. 审批完成不是严格幂等操作，双击或并发请求主要依赖先读后写和数据库状态，缺少幂等记录或原子条件更新。
2. 工单状态变化后，相关旧申请缺少自动 `superseded` 或失效规则。
3. 两个管理员同时批准或批准与撤销并发时，需要并发测试和明确结果。

这类问题属于生产级一致性，不应只靠前端禁用按钮解决。

### P1-4 Android 记住密码

**核查结论：`confirmed`，当前实现确实保存明文密码。**

当前事实：

1. “记住密码”把密码以明文 JSON 写入 `SharedPreferences`。
2. 登录令牌也存储在应用私有 `SharedPreferences`。
3. 文件名是应用私有存储，并不等于密码是加密的。

建议：

1. 取消存储明文密码。
2. 使用 Android Keystore 加密需要持久化的凭据或令牌。
3. 或改为保存短期登录令牌，并设计刷新、失效和退出清除规则。
4. 保留“记住账号”不受影响。

这是安全改进建议，具体实现方式需要结合现有登录令牌策略设计。

### P1-5 身份证必要性

**核查结论：`decision-needed`，不是已确认缺陷。**

当前事实：

1. 客户此前提出了身份证资料管理能力。
2. 当前数据库保存身份证原文，列表和非本人场景进行脱敏。
3. 数据库和备份未做字段级加密。
4. App 用户协议已经写明身份证可能用于身份核验和生产追溯。

需要客户确认：

1. 完整身份证是否确有必要。
2. 能否使用工号或员工编号替代。
3. 如果保留，查看权限、保存期限、字段加密和备份安全如何处理。
4. 是否经过客户法务评估。

### P1-6 PC 和平板同时维护主数据

**核查结论：`proposal`。**

当前事实：

1. 平板和 PC 都只允许管理员维护辅料和配方。
2. 现有日志接口记录的主数据修改并不完整，无法依赖现有审计表回答“谁在现场改了什么”。

建议讨论：

1. 配方修改二次确认。
2. 明确提示“只影响未来工单，不改变进行中工单”。
3. 主数据修改记录修改前后关键字段。
4. 对进行中工单不受影响的提示进行可见性优化。

### P1-7 审计日志

**核查结论：`partial`，且现状比 GPT 描述更严重。**

当前事实：

1. 已有 `audit_logs` 表和只读 API。
2. PC 前端已有 API 方法，但没有审计日志页面。
3. 当前显式写入审计日志的场景很少，主要覆盖备份和部分管理员密码恢复、BUG 反馈。
4. 工单审批、接管、撤销、扫码确认、称重提交、标签生成、主数据新增编辑和账号审批等关键操作没有统一写入审计日志。

因此不能只“补一个审计日志页面”。需要先明确审计事件范围，再把关键状态变化写入同一可查询结构。

最低建议覆盖：

```text
登录成功/失败
账号创建/审批/停用/重置密码
主数据新增/编辑/删除
工单创建/审批/接管/撤销/完成
类型确认/无码放行/称重提交
标签生成/打印状态/重打/作废/复核
备份/恢复
```

## 5. P2 意见核查

| 建议 | 结论 | 说明 |
|---|---|---|
| 电子秤直连 | 合理，但当前不进入第一版 | 前提是客户接受人工读秤风险；否则提升为 P0 |
| 产品和配方 Excel 导入导出 | 已确认需求，但当前只实现辅料导入和模板导出 | 应作为功能缺口，而不是普通 P2 |

| PostgreSQL | 暂不采用 | 先验证 SQLite 并发、锁和故障恢复 |
| 平板离线队列 | 继续推迟 | 离线冲突和证据同步复杂，第一版明确不做 |

补充：Excel 需求在需求基线中写的是“支持后台手工录入和 Excel 模板导入/导出”。当前仅辅料支持模板下载和导入，产品、配方未实现 Excel 导入导出；现有“导出”按钮是工单 CSV，不是主数据导出。

## 6. GPT 未直接指出但应补充的缺口

### 6.1 二维码只校验 materialId，不校验 labelId

这是标签防错链路中的独立缺口：

1. 二维码内容包含 `labelId`。
2. 平板解析时只提取 `materialId`。
3. 后端收不到 `labelId`，无法确认标签是否真实存在。
4. 后端无法检查标签是否作废或重复使用。
5. 任意生成内容为 `{"materialId":"MAT-00023"}` 的二维码都可能通过类型匹配。

在没有恶意攻击者时，这仍会影响标签追溯和作废控制；在需要防伪时，它是明确的安全缺口。

### 6.2 Android 地址格式只支持 `192.168.x.x`

1. App 设置界面固定补齐 `http://192.168.`。
2. 当前客户网络可能使用 `10.x.x.x`、企业网段或 DHCP 保留地址。
3. 正式网络方案需要与 IP 输入、平板配置和 Windows 地址检测一起确认。

### 6.3 自动备份开关具备误导性

设置页显示“自动备份已启用”，但实际没有调度器。正式版本不能保留“界面显示已启用但后台不执行”的状态。

### 6.4 恢复流程缺失

目前不仅缺证据备份，也缺：

1. 备份完整性验证。
2. 数据库与文件一致性。
3. 恢复前备份。
4. 恢复失败回滚。
5. 恢复演练记录。

## 7. 建议吸纳的优先级

以下只是核查后的建议排序，尚未转成正式需求：

### 第一组：生产闭环

1. 真实打印机链路和标签状态机。
2. 扫码同时提交并校验 `labelId`。
3. 标签粘贴后的复核规则。
4. 无码放行审批人、自批限制和异常统计。
5. 完整备份、恢复和演练。
6. Windows 11 全新安装、升级和完整工单验收。

### 第二组：可靠性和安全

1. SQLite WAL、`busy_timeout`、短事务和并发测试。
2. 审批、工单状态变化的幂等和原子条件更新。
3. HTTPS 或书面的受控 HTTP 风险接受。
4. 证据 SHA-256 和不可覆盖检查。
5. Android Keystore，停止明文保存密码。

### 第三组：可审计和可维护

1. 扩展审计日志覆盖范围。
2. 增加可按时间、人员、工单、动作和结果筛选的审计页面。
3. 主数据修改记录前后差异。
4. 正式网络地址和 App 配置优化。

### 暂不采纳或暂缓

1. 辅料启用/停用：与客户已确认规则冲突。
2. 立即迁移 PostgreSQL：缺少证据支持，优先验证 SQLite。
3. 第一版离线队列：现有范围明确不做。
4. 复杂批次、供应商码映射和自动图片识别：继续留在后续版本。
