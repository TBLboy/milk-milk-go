# 决策权限矩阵 v0.2

## 判断顺序

先问五件事：

1. 是否改变用户可感知行为或业务语义？
2. 是否影响数据、安全、隐私、权限或合规？
3. 是否改变公开接口、外部依赖、持续费用或交付范围？
4. 是否难以回滚，或失败会造成较大损失？
5. 用户是否已明确保留该类决定权？

任一高影响项为“是”，通常为 C。否则按可逆性和影响范围区分 A/B。

## A — Agent 直接决定

特征：局部、低风险、可逆、不改变业务语义，有明确工程惯例。

常见例子：

- 命名和格式；
- 局部文件组织；
- 不改变行为的重构；
- 明确小缺陷；
- 补充已有行为的聚焦测试；
- 采用项目已统一的工具或模式。

无需打断用户，可在任务结果中简要留痕。

## B — Agent 决定并记录

特征：有一定工程影响，但仍容易回滚，不改变已确认产品语义。

常见例子：

- 内部模块边界；
- 辅助依赖和封装方式；
- 内部缓存/日志结构；
- 非公开数据结构；
- 测试组织；
- 可回滚的性能优化；
- 小范围架构适配。

必须写 decision-log，记录条件、风险和 reversal plan。

## C — 用户决定

特征：改变业务、范围、数据、安全、外部承诺、费用或不可逆性。

常见例子：

- 新增/删除用户可感知行为；
- 改变业务规则、权限和流程；
- 删除、迁移或不可逆转换数据；
- 认证、授权、隐私和安全策略；
- 改变公开 API/协议；
- 引入持续费用、商业许可或供应商锁定；
- 重大架构迁移；
- 缩减交付范围或接受关键风险。

询问格式：

1. 一个明确问题；
2. 推荐选项；
3. 推荐理由；
4. 各选项业务/工程影响；
5. 是否存在安全默认值。

一次只问当前关键路径上影响最大的一个问题。

## 升降级

- 看似技术问题但会影响产品行为，应升级为 C；
- 多个技术选项若仅是内部可逆实现，不应因为“有选择”就升级为 C；
- 紧急 hotfix 可先采取最小可逆保护措施，但必须记录临时性和后续 C 级确认任务。
